# E2 official synthetic checks (X.3): prerequisite, parts, summaries and what is kept

This procedure implements the X.3 step of the E2 addendum (section 11 and Annex B step 3) once E2 is registered. Section 11: "These are the AT-15 and AT-16 checks adapted to E2. They are run after registration and before any MGSX value is read, without tuning the pipeline." Annex B fixes the order X.1, X.3, X.2, X.4, X.5: the checks use constructed series only and come before the download. The runner is `tools/run_e2_checks.py` and the plan of parts is `tools/plan_e2_x3.py`; the analysis code is the package `src/uc_e2`. The readings the code takes are listed in `docs/E2_READINGS.md`.

## 0. Before X.3: the onsets record (X.1)

After registration, at the research root that holds the tag `h1-frozen`, write the section 7 onsets record once:

```text
python tools/e2_onsets.py --root .
```

It applies the section 7 rule to the growth of the H1-registered ABMI file (verified against its acquisition record) and writes `audit/E2_ONSETS.json`, which it never overwrites; no unemployment value is read. Commit the record. Every registered E2 check reads it and refuses unless its W = 40 eligible onsets are exactly the two of the text, 77 and 148 (sections 7 and 11; reading R14).

## 1. Gates used by every registered step

- **Registration**: `verify_extension_gate` and `check_registration_receipt` of the root's own `tools/run_e_checks.py`, loaded by path and reused unchanged: a clean checkout, the annotated tag `prereg-E2` published identically on origin, `prereg/E2.md` equal to the tagged file, and `audit/E2_REGISTRATION.json` showing an approved public registration of the tagged bytes.
- **Code location**: `tools/run_e2_checks.py`, `tools/run_e_checks.py`, `uc_e2`, `uc_ext` and `uc_core` are the research root's own files; the runner is started from the root with `--root` naming that root.
- **Environment**: the research lock under Python 3.12.14 and a clean tree (`run_e_checks.run_identity`). Outputs go outside the tree or to a git-ignored path (`runs/`).
- **Design**: registered mode takes only the registered design: master seed 1927; the stream ids of Annex A (size: generation 5220, cell 0, replicate i; surrogates 5221, cell 0, replicate i; power: generation 5230, cell = kappa index, replicate i; fixed-onset surrogates 5231, matching cell and replicate); 200 series per cell; B = 1,000 attempts per series; kappa 1.0, 1.2, 1.4, 1.6. It has no size, B or seed option.

A refusal stops the step before any series is generated and before anything is written.

## 2. Prerequisites (Annex B step 3)

On the commit that will run the parts, from a clean checkout under the lock and Python 3.12.14:

```text
mkdir -p runs/extensions/E2
python tools/plan_e2_x3.py > runs/extensions/E2/plan.json
python tools/run_e2_checks.py e2 prerequisite --registered --root . --out runs/extensions/E2/x3_prerequisite.jsonl
python -m pytest -q -p no:cacheprovider tests/test_e2_data_rules.py
```

The prerequisite record holds AT-12 through the E2 spectral-radius function (stream 2012, 100,000 draws, AT-12's tolerances), the reduction of the VAR code with one variable to H1's rolling M(t) at W = 32, 40 and 48 to 1e-10 on the H1-design series of stream 5220, cell 1, replicate 0, F4 as passed in the research record (D-019) and the name of the unit-test file of the section 4 and section 7 rules, whose output is kept as a log beside it. The command exits with status 0 only if every part passed. The section 4 tests that need a file (header records, the release-date record, the classification of fields) belong with the X.2 tool and are added to the evidence when that tool exists.

## 3. Run the parts

The plan lists 40 parts of 25 series: eight size parts (`x3_size_r000-025.jsonl` to `x3_size_r175-200.jsonl`) and eight parts for each power cell (`x3_power_c0_r000-025.jsonl` to `x3_power_c3_r175-200.jsonl`); each argument vector names the prerequisite record, for example:

```text
python tools/run_e2_checks.py e2 size --registered --root . --replicates 0:25 --prerequisite runs/extensions/E2/x3_prerequisite.jsonl --out runs/extensions/E2/x3_size_r000-025.jsonl
```

The parts cover each of the 200 size and 4 x 200 power coordinates exactly once (tested through the runner's own argument parser). Run them in parallel, at most one per physical core, with `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1` and `MKL_NUM_THREADS=1` set in the environment of every part. The runner does not change these variables; it records them, as found, in the session line that every start appends.

Each part file starts with a manifest line (extension, check, mode, master seed, sizes, kappa grid, settings with the power onsets and their source, stream ids, the environment identity, the imported sources with the code hash `code_sha256`, E1's own identity `e1_code_sha256`, the gate record and the prerequisite record's path and SHA-256), then a session line per start, then one line per series. A series line holds the generated series and its SHA-256, the observed statistic, the fitted null with its residual matrix, every attempt's status and statistic, the counts, the p-value, the generator states before and after and the W = 40 window fits of the series (reading R9); it repeats mode, master seed, B, settings, the code hash and `registered`, and holds nothing time-dependent. The lines of the parts of one cell, in plan order, are the lines one process would write for the whole cell (tested at development size).

An interrupted part is resumed by starting the same command again. The runner resumes only into a file whose manifest fingerprint matches the run, after re-verifying every saved line against the manifest, its stored series against its SHA-256 and that SHA-256 against the series regenerated from its seed coordinates. A last line cut off by the interruption is refused: remove that line by hand and start the command again. Do not edit, merge or delete part files.

## 4. Summarise

```text
python tools/run_e2_checks.py e2 summarize --registered --root . --out runs/extensions/E2/x3_size_r000-025.jsonl ... --out runs/extensions/E2/x3_size_r175-200.jsonl
```

`summarize` requires the files of one check to share one fingerprint and to hold disjoint coordinates, re-verifies every line and prints the files' SHA-256 and fingerprints with the summary of `uc_ext.common`: size passes with a rejection rate in [0.02, 0.09] and all 200 replicates valid; power passes with all four cells valid and no adjacent decrease flagged (H1 section 9), D80 reported when defined.

## 5. What must not change between X.3 and X.4

Annex B: "Run and record the §11 size and power cells, commit, and do not change the code again before X.4." The code identity is E1's set (the environment identity, every `uc_core` and `uc_ext` source and `tools/run_e_checks.py`) plus every `src/uc_e2/*.py` and `tools/run_e2_checks.py`; E1's own identity is recomputed beside it and must remain E1's frozen identity. A change to any of these files after the checks forces them to be run again. `audit/E2_ONSETS.json` is read by every registered check and is not changed either.

## 6. Evidence to hash

The prerequisite record and the log of `tests/test_e2_data_rules.py`; `plan.json`; every part file; the two summaries; the command logs (arguments, start and end times, exit status, standard output and error of every process); and `audit/E2_ONSETS.json`. The SHA-256 of each is recorded when X.3 finishes.
