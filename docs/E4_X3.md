# Registered E4 official synthetic checks (X.3): parts, summaries and the record

This procedure implements the X.3 step of the registered addendum `prereg/E4.md` (OSF dpxqf; section 11 and Annex B step 3). Section 11: "These are the AT-15 and AT-16 checks adapted to E4. They are run after registration and before any real-time level is read." The checks use constructed series only. The runner is `tools/run_e4_checks.py`, the plan of parts is `tools/plan_e4_x3.py`, and the record is written by `tools/record_e_x3.py e4` to `audit/E4_X3.json`, which the later E4 gates read (`src/uc_ext_official/gates.py`: `check_x3`, `check_code_frozen`).

## 0. Gates used by every registered step

- **G4**: the runner's gate, which is `verify_extension_gate` and `check_registration_receipt` of the root's own `tools/run_e_checks.py`, reused unchanged: a clean checkout, the annotated tag `prereg-E4` published identically on origin, `prereg/E4.md` equal to the tagged file, and `audit/E4_REGISTRATION.json` showing an approved public registration whose archived `E4.md` has the tagged bytes.
- **Code location**: `tools/run_e4_checks.py`, `tools/run_e_checks.py`, `uc_e4`, `uc_ext` and `uc_core` are the research root's own files; the runner is started from the root with `--root` naming that root.
- **Environment**: the research lock under Python 3.12.14 and a clean tree (`run_e_checks.run_identity`, the mechanism of the E1 and E3 checks). Outputs go outside the tree or to a git-ignored path (`runs/`).
- **Design**: registered mode takes only the registered design: master seed 1927; the stream plan of Annex A (size: generation 5420, cell 0, replicate i; surrogates 5421, cell j = synthetic vintage 0-4, replicate i; power: generation 5430, cell = kappa index; surrogates 5431, cell = 10 x kappa index + j); 200 series per cell; B = 1,000 attempts per synthetic vintage; kappa 1.0, 1.2, 1.4, 1.6. It has no size, B, seed or stream option.

A refusal stops the step before any series is generated and before anything is written.

## 1. Prerequisites and their evidence (before the parts)

Annex B step 3: "Pass the prerequisites, as in E1: F1 (plan p. 7); AT-1 to AT-4 through the same estimator (research code `uc_core.ar`); and unit tests of §§4, 5 and 7 on constructed workbooks and availability tables", and then "Run the §11 cells, commit and freeze the code." On the commit that will run the parts, from a clean checkout under the lock and Python 3.12.14, produce and keep as log files:

- **F1**: the F1 status as the repository records it (`audit/FOUNDATIONS_REPORT.md`), as recorded for E1 in `audit/e1_x3/preflight/PREFLIGHT.json` (check `f1`), with its caveat.
- **AT-1 to AT-4 through `uc_core.ar`**: the same checks as recorded for E1 in `audit/e1_x3/preflight/PREFLIGHT.json` (check "AT-1 to AT-4 through uc_core.ar").
- **Unit tests of sections 4, 5 and 7**: `python -m pytest -q -p no:cacheprovider tests/test_e4_table.py tests/test_e4_vintage.py`, with its output. Two cases of the Annex B list, "a failed observed statistic" and n_v on each side of 55, are tested in `tests/test_e4_procedure.py`, whose log may be added. The case "a title or notes naming another edition" belongs to the X.2 source stage (`docs/E4_READINGS.md`, R-4.12), and its test log, once that stage exists, may be added in the same way.

These logs are hashed into the record with `--evidence` (section 3); they are recorded, not evaluated. The section 11 cells themselves enter the record through their output files.

## 2. Run the parts

```text
mkdir -p runs/extensions/E4
python tools/plan_e4_x3.py > runs/extensions/E4/plan.json
```

The output directory must exist before the parts start (the runner does not create it). The plan lists 40 parts of 25 series by default: eight size parts (`runs/extensions/E4/x3_size_r000-025.jsonl` to `x3_size_r175-200.jsonl`) and eight parts for each power cell (`x3_power_c0_r000-025.jsonl` to `x3_power_c3_r175-200.jsonl`). `--parts-per-cell` changes the split. The parts cover each of the 200 size and 4 x 200 power coordinates exactly once (tested through the runner's own argument parser). Each part is one process, started from the research root with the argument vector the plan gives, for example:

```text
python tools/run_e4_checks.py e4 size --registered --root . --replicates 0:25 --out runs/extensions/E4/x3_size_r000-025.jsonl
python tools/run_e4_checks.py e4 power --registered --root . --cells 0 --replicates 0:25 --out runs/extensions/E4/x3_power_c0_r000-025.jsonl
```

Run the parts in parallel, at most one per physical core. Set `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1` and `MKL_NUM_THREADS=1` in the environment of every part (the plan lists them). The runner does not change these variables; it records them, as found, in the session line that every start appends.

Each part file starts with a manifest line (extension, check, mode, master seed, sizes, kappa grid, settings, stream plan, the environment identity, the imported sources with the code hash `code_sha256`, E1's own identity `e1_code_sha256`, and the gate record), then a session line per start, then one line per series. A series line holds the whole replicate: the generated series and its SHA-256, the observed statistic and its five components, the fitted null of each synthetic vintage with its residuals (`null_models`; Annex B: "each vintage's fitted null and residuals" are retained), every attempt's statistic and components, the counts, the p-value and the generator states before and after; it repeats mode, master seed, B, settings, the code hash and `registered`, and holds nothing time-dependent. The lines of the parts of one cell, in plan order, are the lines one process would write for the whole cell (tested at development size).

An interrupted part is resumed by starting the same command again. The runner resumes only into a file whose manifest fingerprint matches the run (mode, seed, sizes, kappa grid, settings, stream plan, both code hashes, commit, interpreter, packages, lock and gate), after re-verifying every saved line: its fields against the manifest, its stored series against its SHA-256, and that SHA-256 against the series regenerated from its seed coordinates. Saved coordinates are skipped. A last line cut off by the interruption (no final newline, or a line that does not parse) is refused: remove that line by hand and start the command again. Do not edit, merge or delete part files.

## 3. Verify, summarise and record

Before recording, check the part files with the independent verifier (`tools/verify_e4_x3.py`; `docs/E4_X3_VERIFICATION.md`), a second implementation written from the registered texts that imports none of the packages it checks:

```text
python -B tools/verify_e4_x3.py runs/extensions/E4 --all --workers 6 --report <a path outside the clone>/verify_e4_x3.json
```

The runner re-verifies each saved line against its manifest and its stored series (against the series' SHA-256, and that against the series regenerated from its seed coordinates); the verifier also recomputes, from the stored series alone, each synthetic vintage's fitted null and residuals, the observed statistic, every surrogate attempt, the p-value, and the cell summaries, and compares them with what the lines hold. It is an additional check: it is not part of the registered pass rule and does not change the code identity. Exit status 0 is wanted before the record is made; a disagreement is settled before anything is recorded (the record is written once). Keep its report with the other logs, and hash it into the record with `--evidence`. Run it once beforehand on development-size files made by the final runner (`python tools/run_e4_checks.py e4 size --out <file> --n-series 3 --B 40`, then `python -B tools/verify_e4_x3.py <file> --development --partial`).

For review, each check can be summarised with the argument vector the plan gives under `summarize`:

```text
python tools/run_e4_checks.py e4 summarize --registered --root . --out runs/extensions/E4/x3_size_r000-025.jsonl ... --out runs/extensions/E4/x3_size_r175-200.jsonl
```

`summarize` requires the files of one check to share one fingerprint and to hold disjoint coordinates, re-verifies every line, and prints the files' SHA-256 and fingerprints with the summary of `uc_ext.common` (`summarize_size`; `summarize_cell` and `summarize_power_cells`: rates, Wilson intervals, adjacent differences with the 1.96-SE decrease flag, mean S and its standard error, D80). The summary has `registered_design` true only for the full registered design made in registered mode. Then record:

```text
python tools/record_e_x3.py e4 --size runs/extensions/E4/x3_size_r000-025.jsonl ... (the 8 size parts) \
    --power runs/extensions/E4/x3_power_c0_r000-025.jsonl ... (the 32 power parts) \
    --evidence <F1 log> --evidence <AT-1 to AT-4 log> --evidence <unit-test log> --evidence <verifier report>
```

The command checks G4, summarises both checks through the runner's registered `summarize` (gate, lock, interpreter, clean tree and every line re-verified), and refuses unless the outputs form one registered run of one code identity with seed 1927, 200 series per cell, B = 1,000, kappa 1.0-1.6 and the stream plan of Annex A, all recording one `e1_code_sha256`. It writes `audit/E4_X3.json` once, whether the checks passed or failed. Review it, commit and push it before any real-time level is read.

## 4. What the record says

- `X3` is "passed" only when both flags are true. `size_passed`: section 11, "Pass: rejection rate between **0.02 and 0.09** inclusive, with all 200 valid. A rejection in the cells is a valid raw p ≤ 0.05, as in H1 §9." `power_passed`: every power cell complete and valid and no adjacent decrease flagged, the H1 section 9 condition that section 11 carries into E4 ("**Reporting and D80.** As H1 §9, including the 1.96-SE decrease flag and the first-raw-crossing D80."), computed by the functions used for E1 (`docs/E4_READINGS.md`, R-11.2).
- `D80` is stated, and is null when undefined. Section 11 records the expected consequence: "E4 has at most four episodes and its cells use five synthetic vintages, so its power on the real vintages may be lower than the cells show, and its D80 may be undefined; the Branch B diagnostic would then be unavailable. This follows from the design and is recorded, not corrected."
- The design: mode, master seed, series per cell, B, kappa grid and the stream plan (`streams`); the inputs with every part file's SHA-256 and fingerprint; the summaries; the hashed evidence.
- `code_sha256` is E4's code identity: the environment identity of the lock and every source that E1's identity hashes (`src/uc_core/*.py`, `src/uc_ext/*.py`, `tools/run_e_checks.py`), plus every `src/uc_e4/*.py` source and `tools/run_e4_checks.py`. `e1_code_sha256` is E1's own identity recomputed by `tools/run_e_checks.py` in the same run; while none of the files in E1's identity has changed (its sources and the environment files listed in section 5) it equals the identity recorded in `audit/E1_X3.json`. The frozen-code gate (`gates.check_code_frozen` for E4) checks it: both the code now running and the E4 X.3 record must state E1's own recorded identity, else X.4 and the level reader refuse.
- The record is a check of the implementation and the per-vintage fixed-date procedure on constructed series, within the registered synthetic design; section 11: "There is no revision noise. The check measures the per-vintage fixed-date procedure, not the effect of revisions. This limit is disclosed." It is not evidence about UK GDP.

## 5. What must not change between X.3 and X.4

Annex B step 3 ends with "commit and freeze the code". Between the first part and the X.4 run, no file in the identity may change: `src/uc_core/*.py`, `src/uc_ext/*.py`, `tools/run_e_checks.py`, `src/uc_e4/*.py`, `tools/run_e4_checks.py`, and the environment files `tools/run_validation.py`, `tools/verify_validation_runner.py`, `prereg/H1.md` and `requirements.lock`; nor may the lock or the interpreter. The frozen-code gate (`check_code_frozen(root, x3, "e4")`) recomputes the identity and refuses X.4 if it differs from the record's `code_sha256`. A change after the first part has run means running every part again under the new identity. `tools/plan_e4_x3.py`, `src/uc_ext_official/`, `tests/` and `docs/` are not part of the identity.

## Development runs

`python tools/run_e4_checks.py e4 size --out <file> --n-series 2 --B 9` (or `power`, `summarize`) runs the same code with the development seed 20260930, stream ids from 9000 and small sizes; every line says mode "development", and such a run can neither pass nor enter the record. The tests `tests/test_e4_runner.py`, `tests/test_e4_x3_record.py` and `tests/test_e4_plan.py` exercise the runner, the record and the plan at development size and every registered refusal that can be shown on a throwaway repository; the registered computation itself is never started by a test.
